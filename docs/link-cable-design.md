# 通信ケーブル（交換・対戦）の設計と見積もり

同じ Wi-Fi の 2 台の iPhone で、ゲームボーイの通信ケーブルをまねる。目当ては「ドラゴンクエストモンスターズ2」（GBC）の交換・対戦。GBA（mGBA）の通信ケーブルは、あとから 8 章で足した。この文書は第 1 段階（設計と見積もり）で書き、親セッションの了承のあと、作りながら分かったことを書き足している（PR ① まで作った。「作ってみて分かったこと」は各所の※）。

決まっていること（親セッションの指示）:

- 方式は BGB 型: 2 台が互いのゲーム内の時刻（サイクル数）を送り合い、相手より進みすぎないよう止まりながら、通信のバイトを渡し合う。通信している間だけ、もたついたり音が途切れたりする。
- 同じ Wi-Fi の 2 台。Bluetooth は Web アプリから使えないので使わない。
- サーバーを置かない（静的な配信〔いまは GitHub Pages〕のまま）。STUN/TURN も使わない。
- ROM は送らない。それぞれの端末にある自分の ROM で遊ぶ。
- 本家コアは、通信に要る最小限だけ書き換えてよい。GitHub にフォークは作らない。
- 市販 ROM では確かめず、自作の通信テスト ROM で確かめる。

以下、本家のパスは本家リポジトリ（`edf90d9`）のルートから。

## 1. 本家の通信部分のいま

`src/serial.rs`（232 行）。

- レジスタは SB（`0xFF01`、`data`）と SC（`0xFF02`、`transfer_enabled` / `is_high_speed_clock` / `is_master`）。
- `Serial::step()` は `AddressBus::sync()`（`src/address_bus.rs`）から **1 M サイクルに 1 回**呼ばれる。
- 親機（内部クロック、SC の bit 0 = 1）で転送中のときだけ、`clock` を数えて 1 ビットずつずらし、受け取るビットは `serial_disconnected_exchange` が常に 1（= 0xFF を受け取る）。8 ビットで転送を終え、割り込み（`interrupt`、IF の bit 3）を立てる。
- 子機（外部クロック、SC の bit 0 = 0）は何もしない（コメントに「slave mode を知らない」とある）。子機で SC に 0x80 を書いたゲームは、いつまでも終わらない転送を待つ。
- **数え方の誤り**: しきい値（通常 512、倍速モード 256、GBC の高速クロック 16 / 8）は 4MHz の T サイクルでの値なのに、`clock` は 1 M サイクルに 1 しか増えない。このため 1 ビットが実機の 4 倍（CPU 倍速モードでは 2 倍）遅い（通常クロックで 1 バイト約 1ms のところが約 4ms）。APU と同じく `get_t_cycle_increment`（通常 4、倍速モード 2）ずつ足せば実機どおりになる。今は「つながっていない」ので 0xFF が遅く届くだけで目立たないが、通信では速さに直に効くので直す。
- セーブステート: `Serial` は `#[derive(Serializable)]` で、**全部の欄**を順に書く（`tools/serializable_derive`。欄を飛ばす指定は無い）。欄を足すとセーブステートの形が変わり、今のセーブステートが読めなくなる。`AddressBus` の書き出しは手書きで欄を並べている（`address_bus.rs` の `serialize`）。

### 2.2 serial.rs の受け渡しの口

`Serial` の欄は**足さない・変えない**（セーブステートの形を守る）。通信の状態は新しい `LinkPort` に持ち、`AddressBus` の欄に足すが、`AddressBus` の `serialize` / `deserialize` には並べない（セーブステートに入らない）。

```rust
// src/serial/link.rs（新規。セーブステートに入らない）
pub(crate) struct LinkPort {
    connected: bool,       // false の間は今までどおり（0xFF を受け取る）
    clock: u64,            // 通信用の時刻。4MHz の T サイクル（倍速モードでも実時間と同じ刻み）
    outgoing: VecDeque<LinkEvent>,   // 相手に送るもの（JS が取り出す）
    incoming: Option<Incoming>,      // 子機として受け取るバイト（いつ・何を）
    master: Option<MasterTransfer>,  // 親機として送っている転送（終わる時刻・相手の返事）
    waiting_reply: bool,   // 親機で、終わる時刻になったのに返事がまだ（JS へ「止まって待つ」を伝える）
}
enum LinkEvent {
    Transfer { seq: u32, at: u64, byte: u8 },  // 親機が送り始めた。at は相手で受け取る時刻（送り始め＋8 ビットの時間）
    Reply    { seq: u32, byte: u8 },           // 子機が返したバイト
}
```

`AddressBus::sync()` で `self.link.tick(double_speed)`（4 か 2 を足す）を呼び、`self.serial.step(&mut self.link)` に変える（`speed_switch.rs` が `serial` の倍速モードを持っているので、刻みは serial 側から取れる）。

動き（つながっている間）:

- **親機（内部クロック）**: SC に bit 7 と bit 0 が立った書き込み（`AddressBus::write_byte` の `0xFF02`）で、転送の始まりを `LinkPort` に知らせる。`Transfer { at = 今 + 8 × 1 ビットの時間, byte = SB }` を送るものに積む。1 ビットずつはずらさない（バイト単位。途中の SB は読めても元の値のまま）。`at` に着いたら、返事が来ていれば SB を返事にして SC の bit 7 を下ろし、割り込みを立てる。返事が無ければ `waiting_reply` を立てて、その命令が終わったところでコアが JS に戻る（JS が返事を待つ）。転送中に SC の bit 7 を下ろされたら、その転送は取り消し（後から来た返事は `seq` で捨てる）。
- **子機（外部クロック）**: JS から受け取った `Transfer` は、時刻 `at` に着いたとき（もう過ぎていたらすぐ）に受け取る。※ 続けて遅れて届いたときに同じ時刻にまとめて受け取ると、子機が次の用意をする間が無く、2 つ目を「用意が無い」で受けてしまう（試験で起きた）。そこで、受け取る時刻は「前に受け取った時刻 ＋ 親機が送った間隔」より前にしない。受け取りを待っているバイトがあれば、`linkStep` は `limit` を越えてもその時刻まで進む（親機は返事を待って止まっているので、追い越すことはない）。そのとき SC の bit 7 が立っていて bit 0 が 0（受ける用意がある）なら、今の SB を返事に積み、SB を相手のバイトにし、bit 7 を下ろして割り込みを立てる。
  - 用意が無いとき: ※ Pan Docs には書かれていない。SameBoy（`Core/gb.c` の `GB_serial_get_data_bit` / `GB_serial_set_data_bit`）に合わせ、SC の bit 7 が 0 なら 0x00 を返し、自分も親機（内部クロック）なら 0xFF を返す。どちらも自分の SB は変えない（両方が同時に親機になったときは、両方とも 0xFF を受け取る＝つながっていないのと同じに見え、ゲームは役を替えてやり直す）。
- **割り込み**: 今の `interrupt` の欄をそのまま使う（IF の bit 3。`interrupts.rs` は変えない）。
- **つながっていない間**: 今の動きのまま（親機は 0xFF を受け取る、子機は待ち続ける）。ただし上の数え方の誤りは直す（つないでいなくても 0xFF が 4 倍早く届くようになる。困るゲームは無い見込み）。
- **切れたとき**: `connected = false` にし、返事待ちの親機の転送は 0xFF で終える。子機の受け取り待ちは捨てる。

### 2.3 セーブステート

- 形は変えない（`Serial` に欄を足さず、`LinkPort` はセーブステートに入れない）。今までのセーブステートは読めるまま、版（7）も上げない。
- つないでいる間の「ロード」（端末内・ファイルとも）は押せなくする。片方だけ時を戻すと、相手との時刻も通信の途中の状態も食い違うため。「セーブ」はできる（通信の途中でセーブしたものを、つないでいないときにロードすると、親機の転送は 0xFF で終わる。ゲームが通信エラーにするだけ）。

### 2.4 WASM の公開 API（`src/wasm/api.rs` に足す）

今の `stepUntilNextAudioBuffer` は残す（つないでいないときはこれまでどおり）。

| 関数 | 内容 |
|---|---|
| `linkSetConnected(connected: boolean)` | つなぐ・切る。つなぐときに通信用の時刻を 0 にし、積んだものを捨てる |
| `linkStep(limit: number): number` | 命令を 1 つずつ実行し、次のどれかで止まって理由を返す。①音のバッファが一杯になった（`playAudioSamples` を呼ぶ）②通信用の時刻が `limit` に着いた ③相手に送るものができた ④親機で返事を待つ。音のバッファは①で返したときだけ空にする（②〜④で止まっても途中までの音は捨てない）。時刻は `f64`（2^53 T サイクル＝約 68 年分まで正確） |
| `linkClock(): number` | 通信用の時刻 |
| `linkTakeEvent(): LinkEvent \| undefined` | 相手に送るものを 1 つ取り出す（`{ kind, seq, at, byte }`） |
| `linkDeliverTransfer(seq, at, byte)` | 相手（親機）からのバイトを渡す |
| `linkDeliverReply(seq, byte)` | 相手（子機）からの返事を渡す |

`linkStep` の止め方は `Emulator::step()`（命令 1 つ）の後に見る。返事待ちの判定は M サイクルごとなので、止まるのは終わる時刻を最大で 1 命令分（24 T サイクルほど）過ぎたところ。

### 2.5 コアの試験（ネイティブ）

本家の `Emulator` は `pub` なので、`core/tests/link.rs` で **1 つのプロセスに 2 台**作り、交互に少しずつ進めて直結する（時刻を完全にそろえられるので、正しさの基準になる）。WASM の中のエミュレーターは 1 ページに 1 台だけ（`thread_local!` の `EMULATOR`）なので、同じ画面に 2 台は置けない。ブラウザでの 2 台は、タブを 2 つ開いて確かめる（5 章）。

## 3. 2 台の進みを合わせる

### 3.1 送り合うもの

DataChannel（順番どおり・落とさない設定）でバイナリのメッセージを送る。

| メッセージ | 中身 | いつ |
|---|---|---|
| `HELLO` | 約束の版、アプリの版、ROM のタイトル、CGB か | つながった直後に 1 回。タイトルが違えば「相手は別のゲームです」と出す（DQM2 は 2 本あるので止めはしない） |
| `TIME t` | 「自分はゲーム内の時刻 t まで進んだ」 | 進んだ分が 4ms（ゲーム内）を超えるごと、と、止まる直前に必ず 1 回 |
| `XFER seq at byte` | 親機が送り始めた（`at` に受け取ってほしい） | `linkTakeEvent` で出たらすぐ |
| `REPLY seq byte` | 子機の返事 | 同上 |
| `PAUSE` / `RESUME` | 一時停止した・戻った | メニューを開く・ホームに戻すなど。相手の画面に「相手が一時停止しています」を出すため |
| `PING` / `PONG` | 往復の時間を測る | 1 秒ごと（つながっているかの確かめも兼ねる） |
| `BYE` | 切る | 「通信を切る」 |

順番どおりに届くので、`XFER` も `TIME` を兼ねる（`XFER` が届いたら、相手はその時刻まで来ている）。

※ PR ② で作った形（`app/src/link/protocol.ts`）: `HELLO` は約束の版とアプリの版だけにし、ROM のタイトルと CGB かは次の `START` に移した。足したのは次の 2 つ。（※ GBA を足したときに約束を版 2 にし、`XFER`・`REPLY` の中身を 32 ビットに、`START` の CGB かを機械の種類にして、`SO` を足した。8.3）

| メッセージ | 中身 | いつ |
|---|---|---|
| `START epoch title cgb` | 自分のコアを通信につないだ（コアの時刻を 0 にした） | ゲームを始めたとき（ROM を読み直すたび）と、道がつながったときにゲームが動いていれば。受けた側も、自分のゲームが動いていればコアの時刻を 0 にする |
| `STOP` | 自分のコアを通信から外した | ゲームを止めた・ROM を切り替える前 |

`TIME`・`XFER`・`REPLY` には `epoch`（時刻を 0 からそろえ直した回数）を付け、違う `epoch` のものは捨てる（そろえ直す前に送られて、まだ届いていなかったもの）。`START` を送る側は `epoch` を 1 増やし、受けた側は自分より大きければそれに合わせる。両方が同時に同じ `epoch` で `START` を送っても、どちらも自分で時刻を 0 にしているのでそろう。相手のゲームが動いていない間は、自分は W だけ進んで止まり、「相手のゲームが始まるのを待っています…」を出す。

### 3.2 どこで止めて待つか

規則は 2 つだけ:

1. **相手より W 以上先に進まない**: 自分の時刻が「相手から最後に聞いた時刻 ＋ W」に着いたら止まり、次のメッセージを待つ。W はゲーム内の 16ms（約 1 フレーム）から始めて、テスト ROM で詰める。※ 測って 32ms にした（3.6）。
2. **親機は返事が来るまで、転送が終わる時刻の先へ進まない**（`linkStep` が「返事を待つ」で止まる）。

子機側は、相手の `XFER` を `at` に受け取る。子機の方が先に進んでいて `at` を過ぎていたら、受け取った時点ですぐ受け取る（少し遅れて届いたのと同じに見える。遅れは W までに収まる）。親機の側はいつも正確（返事を受けるまで止まるので）。

止まった側は `setTimeout` を予約せず、メッセージが届いたら（`onmessage`）すぐ続きを走らせる（`setTimeout` の最短の待ち〔WebKit で 7ms ほど〕に引っかからない）。両方が同時に「相手より W 先」で止まることは無い（止まる直前に必ず `TIME` を送るので、遅い方は必ず進める）。両方が親機で返事待ちになっても、互いの `XFER` に 0xFF を返すので抜けられる。

### 3.3 音で進む今の作りとの噛み合わせ

`useAudioSync.ts` の `step` の中で、つないでいるときだけ `stepUntilNextAudioBuffer()` の代わりに次を回す:

```
while 音をためる必要がある:
    r = linkStep(min(相手の時刻 + W, 今の時刻 + 4ms))
    積まれたものを全部送る（linkTakeEvent）／4ms 進むごとに TIME を送る
    r が「音が一杯」なら（playAudioSamples が呼ばれ済み）続ける
    r が「W に着いた」「返事を待つ」なら、TIME を送ってループを抜け、setTimeout は予約しない
        → メッセージが届いたら step() を呼び直す（同時に 2 本走らないよう、走っているかの印を持つ）
```

- 1 回の `linkStep` を 4ms で区切るのは、`TIME` をこまめに送るため（相手が W で止まりにくくなる）。WASM の呼び出しが 1 バッファあたり 3 回ほどに増えるだけで、重くはない見込み。
- 止まっている間は音の予約が途切れるので、その分の音が欠ける（「通信中は音が途切れる」）。0.1 秒を超える遅れは今の `MAX_LAG` で合わせ直すので、通信のあとに速く進み続けることはない。
- 一時停止（メニュー・確認を開く・ホームに戻す）は今のままループを止め、`PAUSE` を送る。相手は W 進んだところで止まる。

### 3.4 倍速

つないでいる間は **×1 に固定**し、倍速ボタンを押せなくする（「通信中は ×1」と出す）。片方だけ速くしても、相手に W 先で止められて、止まる・進むを繰り返すだけになるため。切ると、つなぐ前の速さには戻さず ×1 のまま（速さは覚えない今の決まりに合わせる）。

### 3.5 待ちが長いとき

| 状態 | 画面 |
|---|---|
| 止まって 0.3 秒たった | ゲーム画面の上に小さく「相手を待っています…」（相手が `PAUSE` 中なら「相手が一時停止しています」） |
| 相手から 5 秒なにも届かない（`PING` も） | 「相手から応答がありません」と「待つ」「通信を切る」 |
| DataChannel が閉じた・ICE が failed / disconnected のまま 5 秒 | 「通信が切れました」と出し、自動で切る（コアは 0xFF を受け取る状態に戻り、ゲームは通信エラーにする） |

ゲーム側の待ち時間（タイムアウト）はゲーム内の時刻で数えるので、こちらが止まっている間は進まない。ゲームが通信エラーにするのは、子機が W まで先に進んでから受け取る分の遅れが、ゲームの待ちより長いときだけ。W を 1 フレームほどにしておけば、まず起きない見込み（テスト ROM で W を変えて確かめる）。

### 3.6 通信中の実効速度の見込み（同じ Wi-Fi、往復 R = 5〜20ms）

- **つないでいるが通信していないとき**: 止まらずに進めるのは、おおよそ W ≥ R/2 ＋ `TIME` の間隔（4ms）＋揺れ のとき。W = 16ms なら R = 5〜10ms で等速、20ms でもほぼ等速（Wi-Fi の揺れで時々止まる）。
- **通信しているとき**: 親機は 1 バイトごとに返事を待つので、1 バイトに実時間で R ＋ 1〜2ms（処理）かかる。

| ゲームがバイトを送る間隔（ゲーム内） | R = 5ms | R = 10ms | R = 20ms |
|---|---|---|---|
| 続けて送る（1 バイト約 1ms、通常クロック） | 約 15%（約 150 バイト/秒） | 約 9%（約 90 バイト/秒） | 約 5%（約 45 バイト/秒） |
| 1 フレームに 1 バイト（16.7ms） | 等速 | 等速 | 約 8 割 |
| GBC の高速クロックで続けて送る（1 バイト約 0.03ms） | 1% 未満（バイト数は上と同じ） | 同左 | 同左 |

※ PR ② で測った結果（Mac の Chrome、`app/link-test.html` で 2 つを 1 画面に並べ、送るものをわざと遅らせた。往復はアプリが ping で測った値）。数字はゲームの進む速さ（1 = 等速）。「通信中」はテスト ROM の親機・子機（転送ごとに 512 M サイクル空ける。等速なら 1 秒に約 620 バイト）。どの組み合わせでも ERR（並びの食い違い）は 0。

| 往復 | 通信していない（W = 16ms） | 通信していない（W = 32ms） | 通信中（バイト/秒） |
|---|---|---|---|
| 0ms（遅れなし） | 1.0 | — | 1.0（約 620） |
| 8ms | 1.0 | — | 0.19（約 120） |
| 22ms | 1.0 | 1.0 | 0.067（約 42） |
| 52ms | 0.57 | 1.0 | 0.029（約 18） |

- 通信中は、見込みどおり 1 バイトに往復 1 回ぶんかかる（往復 8ms で 1 秒に約 120 バイト、22ms で約 42 バイト）。W を変えても通信中の速さは変わらない。
- 通信していない間の速さは、W が往復の半分＋α を下回ると落ちる（2W / 往復 にほぼ合う）。iPhone の Wi-Fi は省電力で遅れが跳ねることがあるので、**W は 32ms（2 フレームほど）にした**。子機が遅れて受け取る長さはこの分まで増えるが、テスト ROM の TOUT（0.5 秒）は起きなかった。
- GBC の高速クロック＋倍速モードでも、往復 22ms で並びは合った（速さ 0.028）。AUTO（役を決める）も遅れがあっても決まった。

実機の通常クロックは最大で約 1KB/秒。たとえば 1KB をまとめて送る交換なら、実時間で 7〜23 秒ほど（その間、画面は動きが遅く、音は途切れ途切れ）。DQM2 が交換でどれだけ送るか、どのクロックを使うかは、市販 ROM を使わない決まりなので確かめられない（危ないところ 7 章）。

遅すぎたときの次の手（今回は作らない）: 子機が受ける用意をしたとき（SC に 0x80）に SB を先に送っておき、親機は返事を待たずにそれを使う（往復待ちが無くなる）。ただし子機が途中で SB を変えると食い違い、巻き戻せないのでデータが壊れうる。交換で使うのは危ないので、テスト ROM と実際の遊びで遅さが我慢できないときに改めて考える。

## 4. つなぎ方（WebRTC ＋ QR）

### 4.1 方式

WebRTC の DataChannel（`ordered: true`、再送あり）で直接つなぐ。`iceServers: []`（STUN/TURN なし）なので、候補は同じ Wi-Fi の中の自分のアドレス（ホスト候補）だけ。最初の接続情報（offer / answer）は QR で往復する。ICE の候補は全部集め終わってから（`icegatheringstatechange` が `complete`、STUN が無いので 1 秒かからない）まとめて QR に入れる（トリクルしない）。

ほかの案: サーバー（シグナリング・Netlify Functions）は置かない決まり。ブラウザは自分で待ち受け（ソケットのサーバー）できないので、WebRTC 以外に端末どうしを直接つなぐ方法は無い。「QR を片道だけにする」案（端末ごとの証明書〔`RTCPeerConnection.generateCertificate`〕を IndexedDB に覚えておき、2 回目からは相手の分を知っているので answer を自分で組み立てる）は、ブラウザごとの SDP の扱いの違いを踏むので、今回は作らない。

### 4.2 手順と画面

メニューに「通信ケーブル」を足す。開くとゲームは止まる（メニューと同じ）。

```
A（先に始める側）                         B（あとから読む側）
「QR を出す」を押す                        「QR を読む」を押す
  カメラの許可（下の注意）                   カメラの許可
  offer を作り、QR ① を出す  ──────────→  カメラで QR ① を読む
  「相手の QR を読む」を押す                 answer を作り、QR ② を出す
  カメラで QR ② を読む  ←──────────────
  つながる → 両方に「つながりました（相手: タイトル）」→ 閉じるとゲームに戻り、通信が始まる
```

- 画面の文言の例: 「同じ Wi-Fi につないだ 2 台で、片方は『QR を出す』、もう片方は『QR を読む』を押してください」「相手の iPhone のカメラでこの QR を読んでください」「つないでいます…」。
- 遊んでいる間: 倍速ボタンのところに「通信中」（往復の時間も小さく出す。例「通信中 8ms」）。メニューに「通信を切る」。
- **コードの貼り付け**（QR の代わり）: QR の下に「コードをコピー」、読む画面に「コードを貼り付け」を置く。カメラが使えないとき（許可しなかった・Mac のタブどうしで試す）に、AirDrop やメッセージで送って貼る。
- QR の中身: SDP から DataChannel に要らない行を落とし、`CompressionStream("deflate-raw")`（iOS 16.4 以降）で縮めて base64url にする。候補が数個なら 300〜500 文字ほどで、スマホの画面からなら楽に読める大きさ（作ってから測る。大きすぎたら、ufrag・pwd・証明書の指紋・候補だけを取り出して相手側で SDP を組み立てる形に替える）。先頭に約束の版を入れ、読んだものが offer か answer かを確かめる（A が A の QR を読むなどの取り違えを知らせる）。
- ※ PR ③ で作った形（`app/src/link/signal.ts`・`webrtcTransport.ts`・`qr.ts`、画面は `app/src/ui/LinkConnect.tsx`）:
  - コードは `RBL1` ＋ 種類（`O` = offer、`A` = answer）＋ 縮めた SDP の **base32**（`0-9A-V`）。base64 を QR のバイトモードに入れたら 530 字ほど（85 マス四方ほど）で、Chromium の偽のカメラの映像（640x480 に 340px で映す）からは読めなかった。数字と英大文字だけにして QR の英数字モードに入れ、候補の付け足し（`generation`・`network-cost`）と `a=ice-options` も落として、マスを少なくした（同じ条件で読めるようになった）。記号が無いので、コピー・貼り付けでも崩れにくい（貼り付けた空白・改行・小文字は許す）。
  - 相手の SDP は、**候補の行を抜いて `setRemoteDescription` し、候補はそのあと `addIceCandidate` で 1 つずつ足す**。SDP の中に候補を入れたままでは、Playwright の Chromium でつながらなかった（同じ候補を `addIceCandidate` で足すとつながった）。
  - 候補を集め終えるのは、`complete`、最初の候補から 0.5 秒、3 秒の上限のどれか早いところ。WebKit は `complete` を知らせないことがあり、3 秒待つとそのあとつながらないことがあった。
  - 「QR を出す」は、先にカメラを開いてから offer を作る（4.3。答えないまま 10 秒たったら、カメラなしで進める）。読む側のカメラは、全体と真ん中の正方形を 1 フレームおきに交互に jsQR で読む。
  - 画面: メニューの「通信ケーブル」→「通信ケーブルでつなぐ」で下から出る。選ぶ（「QR を出す（先に始める）」「QR を読む」）→ QR とコード（「コードをコピー」）→ 読む（カメラと、貼り付けの欄）→「つながりました（相手のゲーム: …）」。読めないコード・取り違え・つながらない（読んでから 20 秒）・カメラが使えないときは文言を出し、「はじめからやり直す」。つながる前に閉じたら、作りかけのつながりは捨てる。

### 4.3 カメラの許可と iOS のホーム画面アプリでの制約

- `getUserMedia({ video: { facingMode: "environment" }, audio: false })`。HTTPS（GitHub Pages）か localhost で動く。iOS 13.4 以降はホーム画面アプリ（standalone）でも使える。ホーム画面アプリでは、起動し直すたびに許可を聞かれることがある。読めたらすぐカメラを止める（`track.stop()`）。
- **Safari はカメラ・マイクの許可が無いページでは、ICE の候補の IP アドレスを隠して mDNS の名前（`xxxx.local`）にする**。同じ Wi-Fi なら mDNS の名前でもつながることが多いが、Wi-Fi によっては mDNS（マルチキャスト）が通らない。そこで **A も QR を出す前にカメラの許可を取ってから offer を作る**（A はどのみち後で QR ② を読むのでカメラが要る）。これで両方の候補が本当のアドレスになる見込み（許可を取った後に候補を集める必要があるかどうかは、実機で確かめる）。
- カメラを使っている間、iOS が音の出し方（オーディオセッション）を切り替えて音量が変わることがある。つなぐ画面ではゲームが止まっているので困らないが、カメラを止めた後に音が戻るかを実機で確かめる。
- **ホームに戻す・画面を消すと、iOS は JS を止め、しばらくすると WebRTC の接続も切れる**。戻ったときに DataChannel が閉じていれば「通信が切れました」になり、QR からやり直す（サーバーが無いので、ICE を張り直す情報を送る道が無い）。短い間（数秒）なら続くこともあるので、`PAUSE` を送ってから止まる。
- QR を読む部品: iOS Safari には `BarcodeDetector` が無いので **jsQR**（Apache-2.0、純 JS、min で約 130KB）を使う。カメラの映像を `<video>` に流し、`requestAnimationFrame` ごとに縮めた画像を canvas から取って読む。QR を出す部品は **qrcode-generator**（MIT、約 20KB）。どちらも「通信ケーブル」を開いたときに動的 import で読み込み、最初の起動を重くしない（Service Worker はビルドしたものを全部キャッシュするので、オフラインでも開ける）。

| とき | 画面 |

| 読んだ QR が違う・壊れている | 「この QR は通信ケーブルのものではありません」／「相手の QR を読んでください（自分の QR を読んでいます）」 |

## 5. 確かめ方

1. **コアのネイティブ試験**（`cargo test`、`core/tests/link.rs`）: 1 つのプロセスで 2 台を直結し、テスト ROM で親機・子機・高速クロック・CPU 倍速モードのバイトの受け渡し、両方が親機になったとき、片方がつないでいないとき（0xFF）を確かめる。`npm run check` に足す。
   - ※ PR ① の試験（`scripts/test-core.sh`）: GB の通常クロック、GBC の高速クロック＋CPU 倍速モード、子機が 1 フレーム近く先に進む（遅れて受け取る）、両方 AUTO で役が決まる、相手に用意が無い（0x00）、つないでいない（今までどおり）、の 6 件。テスト ROM は受け取った値から次に送る値を決めるので、2 台の間を流れたバイトの並びが式どおりなら、両方が正しく受け取れている。1 秒に受け渡せたのは、通常クロックで約 620 バイト、高速クロック＋倍速モードで約 3,400 バイト（どちらも ROM が転送ごとに 512 M サイクル空けるため）。
   - ※ テスト ROM は、子機の受け取りの続き（次のバイトの用意）を割り込みの中ですぐ行う。フレームごとの画面の処理の後に回すと、高速クロックでは親機の次の転送に間に合わない（実機でも同じ）。
2. **自作の通信テスト ROM**（`testroms/link/link.asm`、RGBDS で書く。※ できた `testroms/link/linktest.gb` も一緒にリポジトリに入れる〔自作なので著作権の問題が無い。`.gitignore` の `*.gb` 除外は市販 ROM のため残し、`testroms/` だけ例外〕。ソースを直したら `scripts/build-testroms.sh` で作り直す。RGBDS は `brew install rgbds`）:
   - A で親機（内部クロック）、B で子機（外部クロック）、SELECT で高速クロック、START で CPU 倍速モードを切り替える。「役を交互に試す」モード（ゲームによくある、子機で少し待って来なければ親機になるやり方）も入れる。
   - 送るのは決まった並び（自分の印＋番号）。受け取った値・数・並びの食い違いの数・1 秒あたりのバイト数を画面に出す。
   - ゲーム内の時刻で数えるタイムアウトを持ち、待ちが長すぎたら「TIMEOUT」を出す（3.5 の「ゲームが通信エラーにする」の再現）。
3. **Mac のタブ 2 つ**: 第 2 段階では BroadcastChannel で同じブラウザのタブどうしをつなぐ試験用の道（`?link=tab`）を作る。第 3 段階では本物の WebRTC をタブどうし（コードの貼り付け）でつなぐ。Chrome と Safari の両方で。
   - ※ 裏に回ったタブは、ブラウザがタイマーを間引く（音を鳴らしていないタブ）。タブを 2 つ開いて片方だけ見ていると、裏のタブが遅れて、表のタブも合わせて 0.03 倍ほどまで落ちた。Mac で試すときは窓を 2 つ横に並べるか、2 つを 1 画面に並べる `app/link-test.html`（`npm run dev` で `/link-test.html`。本番ビルドには入らない）を使う。iPhone 2 台では、どちらも前に出しているので起きない。
4. **遅れをわざと入れる**: 送る道の手前に、遅れ（`?linkDelay=10`、片道 ms）と揺れ（`?linkJitter=5`）を入れる部品を挟む（順番は崩さない）。R = 5・10・20・50ms で、テスト ROM の 1 秒あたりのバイト数と TIMEOUT の有無を測り、W を決める。結果はこの文書に書き足す。
5. **iPhone 2 台**（人に頼む）: 同じ Wi-Fi のホーム画面アプリどうしで、つなぐ・テスト ROM・片方をホームに戻す・Wi-Fi を切る。最後に DQM2 で交換と対戦（人が自分の ROM で）。
6. ※ PR ③: iPhone の実機が無いので、Playwright（1.64.1）の WebKit で、`/link-test.html?mode=webrtc` の 2 つの iframe を 2 台に見立てて、QR を出す → 偽のカメラ（getUserMedia を、相手の QR の画像を描いた canvas の映像に差し替える）で読む → つながる → テスト ROM で受け渡す、を通した（`scripts/link-e2e.mjs`。6 回とも成功、コードの貼り付けでも成功、受け渡しは等速で ERR 0）。
   - 2 台を別々のブラウザコンテキスト（別のプロセス）にすると、WebKit も Chromium もつながらなかった。素の `RTCPeerConnection` 2 つでも同じで、候補は mDNS の名前（`xxxx.local`）だけ、相手からの返事が 1 つも来なかった。この Mac では、ブラウザのプロセスが mDNS の名前を引けない・同じネットワークの中へ送れない（macOS の「ローカルネットワーク」の許可が無いためと見ている）。同じページの中なら、WebKit は自分の名前を自分で引けるのでつながる。Chromium は同じページでも `.local` を引けず、本当のアドレスを候補に出すフラグ（`--disable-features=WebRtcHideLocalIpsWithMdns`）を付けても、この Mac では安定してつながらなかった（QR を読むところまでは通る）。
   - つまり、**別々の端末どうしで本当につながるかは、iPhone 2 台で人に確かめてもらうしかない**。iOS の Safari はカメラを使っている間は候補に本当のアドレスを出すので（4.3）、mDNS の名前が引けなくてもつながる見込み。

## 7. 危ないところ・できないかもしれないところ

- **DQM2 で確かめられない**: 市販 ROM を使わないので、DQM2 の交換・対戦のやり方（送る量、クロック、待ち時間、バイトごとの間隔）は分からない。テスト ROM で通っても、DQM2 で通信エラーになることはありうる。最後は人に DQM2 で試してもらい、だめなら W や子機の受け取り方を詰める。
- **遅さ**: 1 バイトごとに往復を待つので、まとめて送るゲームでは通信中が実時間で 7〜20 倍遅くなる（3.6）。特に GBC の高速クロックを使うゲームは、ゲーム内では一瞬の通信が数秒〜数十秒になる。DQM2 がこれなら我慢できない遅さかもしれない（3.6 の「次の手」）。
- **通信中のボタン**: 通信中はゲームが 0.03〜0.2 倍ほどでしか進まないので、実時間で短く押したボタンは、ゲームの中では 1 フレームより短い押下になり、フレームごとにボタンを読むゲームでは取りこぼすことがある（テスト ROM の SELECT・START で起きた）。交換のデータを送っている間に操作することは少ない見込みだが、困ったら「離したことをコアに伝えるのを、ゲームの中で 1 フレーム進むまで遅らせる」を足す。※ PR ③ で足した（DQM2 の交換メニューの操作に効くため。`app/src/emulator/gameKeys.ts`・`linkSession.ts` の `deferRelease`）。つないでいる間だけ、押してからゲームの中で 1 フレーム（70224 T サイクル）たつまで離すのを遅らせる。往復 22ms・0.07 倍の速さで、実時間 80ms（ゲームの中で 6.4ms）の SELECT が、ゲームの中で 19ms まで押したままになり、テスト ROM が受け取った。
- **バイト単位**: ビットを 1 つずつはずらさない。転送の途中で SB を読む、SC を細かくいじるなどのゲームは動かない（まれ）。
- **子機の用意が無いときの実機の動き**（2.2）は SameBoy に合わせたが、SameBoy にも「外部クロックで転送を始めたときにどうなるか」は TODO と書かれている。実機と違えば、役を交互に試すゲームで食い違うことがある。
- **本家の通信の誤りを直すと、つないでいないときの動きもわずかに変わる**（0xFF が 4 倍早く届く）。困るゲームは無い見込みだが、①のあとに今遊んでいるゲームが普通に動くかを確かめる。
- **iOS の WebRTC**: mDNS の候補（4.3）、ホームに戻すと切れる、オーディオセッションの切り替え、ホーム画面アプリでのカメラの許可の聞かれ方。どれも実機でしか分からない。
- **Wi-Fi の設定**: 端末どうしの通信を禁止する Wi-Fi（ゲスト用・公衆・一部のメッシュ Wi-Fi）ではつながらない。インターネット共有で逃げる。
- **iPhone の処理の重さ**: 1 バッファに `linkStep` 数回とメッセージの処理が足される。倍速 ×2 が回る端末なので足りる見込みだが、②で古い iPhone 相当（CPU を 4 倍遅くした Chrome・WebKit）でも測る。
- **QR の大きさ**: SDP が思ったより大きいと、QR が細かくなってカメラで読みにくい（4.2 の替え方）。

## 8. GBA の通信ケーブル

GB・GBC の通信（1〜7 章）ができたあとで、GBA（mGBA 0.10.5 の WASM。スレッドなし）にも通信ケーブルを足した。目当ては、テイマーズライフ GBA 版の通信の配合（お見合い）と夢の花のおすそ分け（決定 #76 #87）。つなぎ方（WebRTC・QR・コードの貼り付け）と進みの合わせ方（待つ方式）は GB と同じものを使い回し、コアの口だけを GBA 用に足した。

### 8.1 GBA の通信の仕組み（SIO）

GBA の通信ポートは、RCNT（`0x4000134`）の bit 15・14 と SIOCNT（`0x4000128`）の bit 13・12 でモードを選ぶ（GBATEK の「GBA Communication Ports」）。

| モード | 何台 | 1 回に送るもの | クロック・速さ | 1 回の長さ（16.78MHz のサイクル） | 主な使い道 |
|---|---|---|---|---|---|
| ノーマル 8 ビット | 2 | 8 ビット（SIODATA8 `0x400012A`） | 親機が出す。256KHz か 2MHz | 512（30µs）／64（4µs） | GB の通信と同じ形。自作の通信 |
| ノーマル 32 ビット | 2 | 32 ビット（SIODATA32 `0x4000120`） | 同上 | 2048（122µs）／256（15µs） | 速く多く送る自作の通信 |
| マルチプレイ | 2〜4 | 16 ビット（SIOMLT_SEND）。全員が全員の分を受け取る（SIOMULTI0〜3） | 親機が決めた 9600〜115200bps | 2 台で 73003（4.4ms）〜6075（0.36ms）（mGBA の `GBASIOCyclesPerTransfer`） | 市販の対戦・交換の多く（ポケモンなど） |
| UART | 2 | 8 ビットずつ（FIFO あり） | 9600〜115200bps | — | ほぼ使われない |
| JOY BUS・汎用（GPIO） | — | — | — | — | GC とつなぐ・周辺機器 |

ノーマルモードの決まり（GB の SB・SC とほぼ同じ）:

- SIOCNT の bit 0 が 1 なら親機（内部クロック）、0 なら子機（外部クロック）。bit 1 は親機のクロック（0 = 256KHz、1 = 2MHz）。bit 12 は長さ（0 = 8 ビット、1 = 32 ビット）。bit 14 は終わったときの割り込み。
- bit 7（Start）を立てると転送が始まり（子機は「受ける用意がある」の意味）、終わると下りる。
- bit 3 は「止まっている間の SO の高さ」、bit 2 は SI（相手の SO）を読むだけのビット。ふつうは子機が用意できたら SO を低くし、親機は SI が低いのを見てから送り始める（GB には無い手順）。

### 8.2 mGBA のいま（0.10.5）

- 通信の口は `struct GBASIODriver`（`include/mgba/gba/interface.h`）。`init`・`deinit`・`load`・`unload`・`writeRegister` を持ち、`GBASIOSetDriver(&gba->sio, driver, モード)` でモードごとに差す。SIOCNT と送るデータのレジスタに書くたびに `writeRegister` が呼ばれ、返した値がレジスタに残る（`src/gba/sio.c`・`src/gba/io.c`）。差していないモードはダミー（ノーマルは 0xFF…を受け取ってすぐ終わる・SI は 1、マルチプレイは自分 1 台）。
- 本家の 2 台つなぎ（`src/gba/sio/lockstep.c`）は、同じプロセスの中の複数の mGBA をスレッドと排他で止め合う作りで、ネットワークもスレッドなしの WASM も考えていない。しかもノーマルモードは途中まで（`// TODO`）で、子機は親機のデータを受け取るが、親機は子機のデータを受け取らず 0xFFFF…になる。0.10 の libretro の口も通信を出していない。
- 1 フレームの途中で止めて JS に戻る口は無いが、`struct GBA` の `earlyExit` を立てると `GBAProcessEvents` がその場で抜け、`ARMRunLoop` が戻る（本家もフレームの終わりと音のバッファが一杯のときに使っている）。時刻の予約は `mTimingSchedule`（`include/mgba/core/timing.h`）。

### 8.3 方式と作り

**GB と同じ「待つ方式（ロックステップ）」をそのまま使う**。互いのゲーム内の時刻を送り合い、相手より W（32ms）以上先に進まない。親機は転送を始めたら中身を送り、転送の長さが過ぎたら子機の返事が来るまで止まる。子機は親機が決めた時刻 `at` に受け取る（もう過ぎていればすぐ）。理由:

- GBA のノーマルモードは GB の通信と同じ形（親機がクロックを出し、1 回で互いのデータを入れ替える）なので、GB で詰めた規則（3 章）と数（W = 32ms、TIME は 4ms ごと）がそのまま使える。
- ほかの案は、どれもゲームの中身に立ち入るか、巻き戻しが要る。たとえば「子機の用意したデータを先に送っておき、親機は待たない」（3.6 の次の手）は、子機が途中でデータを変えると食い違い、巻き戻せない。マルチプレイの「先読み（GBA の Link Cable を Wi-Fi にする Dolphin・Switch Online の作り）」も、ゲームごとの手当てが要る。テイマーズライフは自作なので、遅さはゲームの側（まとめて送る・32 ビットで送る）で吸収できる。
- mGBA を書き換えずに済む。ドライバーは本家の公開の口（`GBASIODriver`）で、止めるのは `earlyExit`。**`mgba/patches/` に足したパッチは無い**（JS からの口 `mgba/glue/mgba-glue.c` に書いた。決定 #45 の「本家は直に書き換えない」のまま）。

作り:

| 場所 | 中身 |
|---|---|
| `mgba/glue/mgba-glue.c` の下の「通信ケーブル」 | ノーマルモード用のドライバーと `gba_link_*`。GB の `linkStep` などと同じ形（表の下） |
| `app/src/link/linkCore.ts`（新規） | コアの口 `LinkCore`（時刻の単位・1 フレームの長さ・つなぐ・進める・取り出す・渡す）。GB（Retro Boy）の分もここ |
| `app/src/gba/gbaCore.ts` | `linkCore()`（GBA の `LinkCore`）と `takeFrameAudio()` |
| `app/src/link/linkSession.ts` | Retro Boy の関数を直に呼ぶのをやめ、`LinkCore` を通す。W・TIME の間隔は ms で持ち、コアの `cyclesPerMs` で直す |
| `app/src/gba/useGbaLoop.ts` | つないでいる間は `session.step()` を回し、1 フレームの区切りで音を取り出して絵を描く。止まったら setTimeout を予約せず、`onWake` で続ける（`useAudioSync.ts` と同じ） |
| `app/src/session/useRomSession.ts`・`emulator/gameKeys.ts`・`ui/RomMenu.tsx` | GBA を始めても通信を切らずにつなぎ直す。ボタンを離すのを 1 フレーム遅らせる（GBA の 1 フレームは 280896 サイクル）。メニューの「GBA では使えません」をやめ、GB と同じ「通信ケーブル」を出す |

`gba_link_*`（GB の 2.4 と同じ考え。時刻は double の GBA のサイクル、つないだときを 0 にする）:

| 関数 | 内容 |
|---|---|
| `gba_link_set_connected(1/0)` | ノーマルモードにドライバーを差す・外す。時刻を 0 にし、積んだもの・途中の転送を捨てる。外すとき返事待ちの親機は 0xFFFFFFFF で終える |
| `gba_link_step(limit)` | `ARMRunLoop` を回し、次のどれかで止まって理由を返す: 1 フレーム進んだ（0。`gba_take_audio` で音を読む）・送るものができた（1）・親機で返事を待つ（2）・`limit` に着いた（3）。`limit` は時刻の予約（`mTimingSchedule`）で `earlyExit` を立てて止める |
| `gba_link_take_event()` と `gba_link_event_*` | 送るもの（転送・返事・SO）を 1 つ取り出す |
| `gba_link_deliver_transfer(seq, at, data, bits)`・`gba_link_deliver_reply(seq, data)`・`gba_link_deliver_so(at, level)` | 相手から届いたものを渡す |

ドライバーの動き:

- 親機: SIOCNT に bit 7 と bit 0 が立ったら、`TRANSFER { seq, at = 今 + 長さ, data, bits }` を積んで `earlyExit`（すぐ JS に戻って送る）。長さが過ぎたら（時刻の予約）、返事が来ていれば SIODATA を返事にし、bit 7 を下ろして割り込みを立てる。来ていなければ返事待ちで止まる。途中で bit 7 を下ろしたら取り消し（遅れて来た返事は seq で捨てる）。
- 子機: 届いた転送は時刻 `at` に受け取る（時刻の予約）。そのとき子機で bit 7 が立っていれば、自分のデータを返事にして相手のデータを置き、bit 7 を下ろして割り込みを立てる。用意が無い・自分も親機なら、自分のデータは変えずに 0xFFFFFFFF を返す（GB は「用意が無い」で 0x00 を返したが、GBA の実機の動きは確かめられないので、つながっていないのと同じ値にした）。8 ビットと 32 ビットが食い違ったときは、それぞれ自分の長さで読み書きする（上の桁は捨てる）。
- SO・SI: SIOCNT の bit 3 が変わったら `SO { at, level }` を送り、相手は時刻 `at` に自分の SI（bit 2）にする。つないだ直後の SI は 1（相手の SO が分からない＝つながっていないのと同じ）。
- **子機は、受け取りを待っている転送があれば、limit（相手の時刻 ＋ W）を越えてもその時刻まで進む**。GB と同じ規則（2.2 の※）だが、GBA では最初これを入れ忘れて、数百回の転送のあとに必ず止まった。子機は「前に受け取った時刻 ＋ 親機の間隔」より前に受け取らないので、子機が W 先まで進んでいると受け取る時刻が W の先になり、親機は返事を・子機は相手の時刻を待ち合う。
- セーブステートには入れない。つないでいる間のロードは、GB と同じく画面で押せなくしてある。

送り合う約束は **版 2** にした（`protocol.ts`。版 1 のアプリとはつながず「相手のアプリの版が違います」が出る）:

- `XFER` の中身を 8 ビットから 32 ビットにし、ビットの数（8・32）を足した。`REPLY` も 32 ビット。
- `SO`（12）を足した（epoch・時刻・高さ）。GB は送らない。
- `START` の CGB か（u8）を機械の種類（0 = GB、1 = GBC、2 = GBA）にした。GBA と GB・GBC は時刻の単位も通信の形も違うので、組が合わなければ進みを合わせず、届いた転送も捨てる（それぞれ 1 台で遊んでいるのと同じ）。メニューに「GBA と GB・GBC のあいだでは通信できません」を出す。

### 8.4 1 フレームに何回やりとりが要るか・遅れ

- 通信していない間は GB と同じ: `TIME` を 4ms（ゲーム内）ごとに送るので、1 フレーム（16.7ms）に片道 4 つほど。ほかに `PING` が 1 秒に 1 つ。W = 32ms なので、往復が 50ms ほどまでは止まらずに等速で進む（下の表）。
- 通信している間は、**転送 1 回に往復 1 回**。GBA のノーマルモードの転送は 4〜122µs（8.1）で、ゲームの中では一瞬なので、遅さはほぼ往復の時間だけで決まる。続けて送るなら、1 秒の転送の回数 ≒ 1 / 往復。32 ビットなら 1 回 4 バイト運べるので、8 ビットの 4 倍速い。
- テイマーズライフで魔物 1 匹のデータを 256 バイトとすると、32 ビットで 64 回。往復 10ms なら 0.7 秒ほど、往復 25ms なら 1.6 秒ほど（その間ゲームはほぼ止まり、音は途切れる）。ゲームの中で数える待ち時間（タイムアウト）は止まっている間は進まないので、通信エラーにはならない。
- マルチプレイを足すとき（8.7）は、1 回が 16 ビットなので、同じ量に 32 ビットの 2 倍の往復が要る。

### 8.5 試験の道と結果

- 自作のテスト ROM「GBA 通信テスト」（`games/linktest-gba/`、C を Homebrew の llvm で。字・配置・ヘッダの道具は `games/gba-bench/` のものを使う。内蔵ソフトに入れたので、iPhone でもメニューから選べる）。A = 親機、B = 子機、SELECT = 8/32 ビット、START = 256KHz/2MHz、下 = 止める。並びは GB の通信テストと同じ式（`m(j+1) = s(j) + 1`、`s(j+1) = m(j) xor 0xA5A5A5A5`）で、受け取った値が式どおりかを OK・ERR で数える。子機は SO を低くして用意を知らせ、親機は SI が低いときだけ送る（SO・SI の受け渡しの試験も兼ねる）。
- `npm run dev` の `/link-test.html`（2 つを 1 画面に並べてタブの道でつなぐ。`?linkDelay=` で片道の遅れ、`?linkJitter=` で揺れ）で、Mac の Chrome（tanacode の中のブラウザ）で測った。数はゲームの進む速さ（1 = 等速）と 1 秒の転送の回数（アプリの数え。ROM は転送のあいだを空けずに送り続ける）。

| 往復（ping で測った値） | 通信していない | 通信中（32 ビット・256KHz） | 通信中（8 ビット・2MHz） | ERR |
|---|---|---|---|---|
| 0ms（遅れなし） | 1.0 | 約 3,090 回/秒（12,360 バイト/秒）、速さ 0.99 | — | 0（46,401 回） |
| 約 10ms | 1.0 | 96 回/秒（384 バイト/秒） | — | 0 |
| 約 25ms | 1.0 | — | 40 回/秒（40 バイト/秒） | 0 |
| 60〜73ms（片道 26ms ＋揺れ 10ms） | 0.92 | 16 回/秒（64 バイト/秒） | — | 0 |

- 遅れなしで速さが 0.99 なのは、転送の長さ（122µs）より JS の往復（同じページの中の BroadcastChannel）が短いため。往復があると、GB（3.6）と同じく 1 回に往復 1 回ぶんかかる。
- 本物の WebRTC: `scripts/link-e2e.mjs` に `ROM=gba` を足し、Playwright の WebKit で QR を出す → 偽のカメラで読む → つながる → テスト ROM で受け渡す、を通した（遅れなしで 1 秒に 1,676 回、ERR 0。ヘッドレスの WebKit で 2 台を 1 つのページで動かしているので速さは 0.55）。GB のテスト ROM でも同じ e2e を流し、今までどおり通ること（1 秒に 571 回）を確かめた。
- GB と GBA を組にしたとき: 両方とも等速のまま、それぞれ 1 台で動き、メニューに 8.3 の文言が出る。GBA から GB・GBC に切り替えても（逆も）つながりは切れず、相手と時刻をそろえ直す。

### 8.6 iPhone 2 台での試し方（人に頼む）

1. 2 台を同じ Wi-Fi につなぎ、どちらもアプリを最新にする（約束の版 2。古い版とはつながらない）。
2. 両方でメニュー →「内蔵ソフト」→「GBA 通信テスト」を始める。
3. 片方でメニュー →「通信ケーブルでつなぐ」→「QR を出す」、もう片方で「QR を読む」。GB と同じ手順で QR を読み合い、「つながりました（相手のゲーム: LINKTESTGBA）」まで進めて、両方「閉じてゲームに戻る」。
4. 片方で B（子機）、もう片方で A（親機）。親機の SI が 0 になり、OK が増え続け、ERR が 0 のままなら成功。画面のボタンの上の「通信中 ○ms」が往復の時間。BPS は 60 フレームごとに出るので、通信中はなかなか変わらない（ゲームがほぼ止まるため）。
5. 余裕があれば: SELECT で 8 ビット、START で 2MHz（両方で同じにしてから A・B）。片方をホームに戻す・Wi-Fi を切る → 「通信が切れました」になり、親機は ERR が 1 つ増え（0xFFFFFFFF を受け取る）、そのあとは WAIT が増える（SI が 1 のまま）。
6. 片方を GB の「通信テスト」にすると、メニューに「GBA と GB・GBC のあいだでは通信できません」が出る。

### 8.7 できないこと・この先

- **マルチプレイ・UART・JOY BUS は作っていない**（ダミーのまま。つながっていないのと同じに見える）。市販の GBA の対戦・交換の多くはマルチプレイなので、市販のゲームの通信は今は動かない（市販 ROM で確かめない決まりなので、もとから狙っていない）。足すなら同じドライバーに `SIO_MULTI` を差し、親機の転送で 16 ビットを送り、子機は SIOMLT_SEND を自動で返し（子機の用意は要らない）、両方が SIOMULTI0・1 を受け取る形になる。3 台・4 台は、待つ方式を全員の時刻の最小に合わせる形に広げる必要がある（WebRTC も 3 本以上になる）。
- ビットを 1 つずつはずらさない（GB と同じ）。転送の途中で SIODATA を読む・SIOCNT をいじるゲームは動かない。
- 子機の「用意が無いとき」の返事（0xFFFFFFFF）と、8・32 ビットが食い違ったときの読み方は、実機で確かめていない。
- 2 台の別々の端末での WebRTC は、GB と同じく iPhone 2 台でしか確かめられない（5 章の 6）。
- テイマーズライフで使うときの決め: 32 ビットのノーマルモードで、子機は割り込みの中で次のデータを用意し、親機は SI を見てから送る（テスト ROM と同じ手順）。送る量をまとめて少なくする。役は、片方が「部屋を作る（子機で待つ）」、もう片方が「部屋に入る（親機）」のように画面で選ばせると、AUTO のような役の決め合いが要らない。
